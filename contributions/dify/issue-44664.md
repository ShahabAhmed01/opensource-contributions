## Issue

"Bug: detect_file_encodings raises misleading error when charset_normalizer returns encoding=None"

Filed 2026-10-23, OPEN, no labels yet. Created alongside PR #44663 per Dify's CONTRIBUTING.md guidance ("Don't forget to link an existing issue OR open a new issue in the PR's description").

## Root cause

In `api/core/rag/extractor/helpers.py`, the `detect_file_encodings()` function checks `all(encoding.encoding is None for encoding in encodings)` BEFORE filtering out None encodings:

```python
# Original buggy logic:
if all(encoding.encoding is None for encoding in encodings):
    raise RuntimeError(f"Could not detect encoding for {file_path}")
return [enc for enc in encodings if enc.encoding is not None]
```

When `charset_normalizer.best()` returns a result where `encoding=None`, the internal `read_and_detect` function creates a `FileEncoding(encoding=None, ...)`. The `all()` check then evaluates to `True` (since the single element has `encoding=None`), raising a `RuntimeError` with the misleading message "Could not detect encoding". The filter that would remove the None encoding is never reached.

## Fix

Filter out None encodings FIRST, then check if any valid encodings remain:

```python
# Fixed logic:
valid_encodings = [enc for enc in encodings if enc.encoding is not None]
if not valid_encodings:
    raise RuntimeError(f"Could not detect encoding for {file_path}")
return valid_encodings
```

This ensures:
1. Valid encodings are preserved even if mixed with None encodings
2. The error message is only raised when truly NO valid encoding was detected
3. The behavior matches the function's documented intent
