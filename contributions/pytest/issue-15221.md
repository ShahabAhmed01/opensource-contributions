## Problem

Reproduced on `49ea4d0` before writing any code: 100 file arguments of
a freshly populated 150-file directory, `--collect-only`, one warm round
each side — 2.31s / 2.34s before, 0.39–0.41s after, identical item ids
and order both ways (the new test asserts exact node id lists). A
plain directory argument has always been populated once and unaffected
(~ 0.64s → 0.39s on the same machine).

## Root Cause

`Session.collect` decides dedup per remaining path part:
`handle_dupes = not (len(matchparts) == 1 and isinstance(matchparts[0],
Path) and matchparts[0].is_file())`. For arguments ending in a file
path, `handle_dupes` is therefore `False` — "files given directly
multiple times on the command line should not be deduplicated" is a
deliberate contract — but it is enforced by *skipping the collection
cache for that call* (`_collect_one_node` with `handle_dupes=False`
re-collects the node fresh every time it is reached). The parent `Dir`
of an explicitly given file is re-collected whole for each file
argument: a node is built for every sibling, `pytest_ignore_collect`
and `pytest_collect_file` fire for each entry per argument, and all
siblings but one are pruned afterwards. On Windows the pruning adds the
#11895 short-path fallback (`samefile_nofollow` — two `lstat` calls per
non-matching sibling per argument), which is where the issue's 44,377
calls came from.

## Solution

- `Session.perform_collect` computes, once per collection,
  `self._repeated_file_arguments` — the set of file-argument paths that
  occur in **more than one** of the initial arguments (from
  `self._initial_parts`, counted per path, file arguments only).
- `Session.collect` keeps a fresh collection (`handle_dupes=False`)
  for those repeated paths — an explicitly given file is never
  deduplicated: `--keepduplicates` runs a file twice and `::`-part
  selections of the same file run it per argument, as before.
- For file arguments collected exactly once it reuses the level's
  cached collection report — parent level scanned once, node ids and
  order unchanged, file itself not deduplicated.
- A cached report that previously **failed** is re-collected fresh, as
  it would have been before successful reports were reused, so
  collection failures and their reports are unchanged.
- The `path_cache` top-level reuse and the per-level cache
  reconciliation from #14635 are untouched; directory arguments were
  never implicated.

## Lessons Learned

- The dedup contract ("files given directly multiple times on the
  command line should not be deduplicated") is load-bearing: parent
  caching must carve **repeated** file arguments out of any reuse, or
  it silently changes `--keepduplicates` and `::`-part semantics. The
  precompute is exactly that carve-out, and two of the four tests pin
  it.
- A performance issue with a measured table and an identical-items
  claim is the strongest acceptance contract available: the test now
  asserts exact node id lists, and both the issue's Windows numbers and
  this environment's Linux numbers (2.31s → 0.39s) are reproducible
  from the diff.
- `codecov/patch`'s conclusion is only meaningful once every
  coverage-enabled job has uploaded: a mid-rollup read reported
  76.47% / failure while jobs were in flight, then success after
  remaining uploads. The local coverage run is the cheap way to tell
  "waiting" from "a line really missed."
- pytest's `CONTRIBUTING.rst` ships an explicit AI/LLM-assisted
  contributions policy: AI-assisted work with human accountability is
  welcome, purely agentic output is closed and its authors banned.
  That policy — not "no AI ever" — is what a prior session had read as
  "drive-by agentic PRs rejected". Owning the distinction in the PR
  body (an `AI assistance disclosure` section) and answering review
  from the account is the whole compliance cost; the account holder is
  the responsible human.
- The PR body is editable after publication: correcting a now-stale
  limitation note (ruff/mypy had not run when written) and adding the
  owed disclosure does not move the head, so no CI rerun either.
